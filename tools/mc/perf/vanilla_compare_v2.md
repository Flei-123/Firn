## Findings
- Vanilla with High performance + no background load is ~2x faster than in the previous run (r8 1280x720: p50 3.99 -> ~2.1 ms). The previous run (Balanced, Firefox/Teams open) is therefore NOT comparable with this series.
- mcplay GL AND Vulkan sit at p50 ~15.6 ms in every cell (= 64 Hz, exactly the Windows timer tick 15.625 ms), independent of radius, resolution and backend. At the same time: world_draw only ~1.4 ms (own statistics), process CPU 7-42 % of a core. => The frame waits ~14 ms; the numbers are a wait limit, NOT render cost. This is the cause of the "bimodal" r8 values in the previous run (7.5 or 15.6 ms depending on the timer state; here with High performance/no background consistently 15.6).
- Suspicion (not proven): the 2 ms socket recv timeout in the frame loop (mc_codec.wire_timeout(2)) is rounded up to the 15.6 ms tick; Windows 11 has per-process timer resolution, mcplay does not call timeBeginPeriod. Roadmap r277.
- mcplay Vulkan was pinned to FIFO (60 fps) in the shipped build (two trial runs: p50 16.67 ms, one present per VSync). New: MCPLAY_VSYNC=0 selects IMMEDIATE/MAILBOX (trial run 15.63 ms = same 64 Hz wait limit as GL).
- RAM: Vanilla client JVM ~1.7-2.1 GB peak WS (2.0-2.4 GB private), mcplay GL ~0.46-0.64 GB, VK ~0.60-0.78 GB (see table).

## Not comparable / limits
- Same world/chunk contents/server, but Vanilla renders shaders, light, entities, weather, sky, particles, biome tint, fancy graphics; mcplay a simpler renderer (no sound in both). No "faster/slower" statement about renderer quality; NOT "faster than Vanilla".
- One spot (spawn), one machine, 22 s per run, 2-3 runs. 640x360 has fewer runs (time limit). Vanilla spread (r16 3.4 vs 5.1 ms between runs) shows residual noise (background services, boost/thermals).
- Load time "start until world visible" only as start->window and start->join; no chunks-ready time. Fabric+Sodium not measured (time).
- CPU % from process CPU time in the measurement window (Vanilla JVM: all threads, GC/chunk meshing included).

- Profile GL r8 (median per frame, us): frame 2040 = net_tick 350 + draw_cpu 1370 (world_cpu 1180 = cull 345 + submit 190 + draw loop 630) + present 270. GPU terrain 0.87 ms (sky 0.1, rest < 0.05). 643 visible, 537 drawn sections, 277k submitted tris.
- Profile GL r16: frame 5040 = world_cpu 3900 (cull 1890 + submit 280 + draw loop 1670) + net_tick 390 + present 260. GPU terrain 2.7 ms. 3865 visible, 2184 drawn, 1.18M tris.
- Verdict: CPU-bound on the render thread (stream_frame: cull BFS, schedule scan, per-section draw collection), identical on GL and VK (VK r8 world_cpu 1050, r16 4240). GPU is ~40-55 % of the frame. Fixed overhead ~0.8 ms even with almost nothing drawn (view 4 + LOD 8: world_cpu 520 of 1300).
- Tried and dropped: cull micro-opts (closed-form pair bit, Ciura gap sort, memset of the window, removing the known-count pass): r16 cull 1894 -> 1939 us = no gain, reverted. Face-direction buckets confirmed (off = slower).
- Result: the renderer alone is NOT 2x Vanilla (r8 1.2x, r16 1.1-1.2x). With LOD at equal view distance mcplay is 2.5-2.6x faster at the Vanilla r16 distance (view 8 + LOD 16: 2.26 vs 5.74-5.97 ms) and ~1.9x at the r8 distance (view 4 + LOD 8: 1.30 vs 2.44-2.51). The far terrain is then simplified LOD, and mcplay still has a simpler renderer than Vanilla (no shaders/entities/particles/weather), so this is not like-for-like.
- Next levers (CPU): sub-profile net_tick (350 us) and the draw loop (1.2 us per drawn section), cache cull result across frames / thread the cull + draw-list build, reduce the 0.8 ms fixed per-frame overhead. GPU at r16 (2.7 ms, 1.18M tris) needs fewer triangles (LOD default for r > 8).
