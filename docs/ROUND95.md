note that in substance the machinery was there (round 12 `comptime`, round 13

## 1. Who was actually asking, and what they were asking

Before anything was built, the question was which code in the engine works
with Unicode data that is not Unicode data. Five places, and none of them was
a guess:

| where | what it had |
|---|---|
| `lib/js/lex.fi` | `ID_Start`/`ID_Continue` out of `lib/js/unicode_id.fi`: 647 + 754 ranges, **generated by a Python script**, Unicode **14.0.0**, pushed into a heap buffer at start up (2,802 calls) and searched with a binary search |
| `lib/js/lex.fi` | `is_space`: a hand written list of the `Zs` category |
| `lib/js/builtin.fi` | `toUpperCase`/`toLowerCase` — the comment said it: *„ASCII plus Latin-1: a full case table is a round of its own"* |
| `lib/js/builtin2.fi` | the same again for `toLocaleUpperCase`/`toLocaleLowerCase`, plus a hand written white space list for `trim` |
| `lib/js/regexp.fi` | `Canonicalize` (22.2.2.9): eight hand written blocks — Greek, Cyrillic, Armenian, fullwidth, circled … |

`lib/html/` was searched as well and has **nothing of the kind**: the WHATWG
tokenizer defines its case handling as ASCII only (13.2.5, „ASCII
case-insensitive"), and `lib/html/mem.fi` implements exactly that in
`cp_eq_ascii_lower`. The character reference table is not Unicode data but
the WHATWG name list, and it is already generated. So the HTML side needed
no change, and its quota is unchanged — that is a result, not an omission.

The bug in `regexp.fi` was found while reading, not while testing:
`U+0131` (dotless i) was mapped to `U+0130`. Its simple upper case is ASCII
`I`, so 22.2.2.9 step 6 („if `ch` ≥ 128 and `cu` < 128, return `ch`") says
leave it alone.

## 2. The build step

`bash tools/ucd/build.sh`. Seven steps, each with a number at the end.

```
-- 0. the data files are unchanged --
   UnicodeData.txt: OK
   DerivedCoreProperties.txt: OK
   UnicodeData.txt            2198209 octets, 40575 lines
   DerivedCoreProperties.txt  1134783 octets, 13601 lines
   Unicode version            17.0.0
```

The sums are pinned in `tools/ucd/UCD.sha256` and compared before anything is
read; `--fetch` loads both files from `unicode.org` again. The version is not
typed in anywhere — it is read out of the first line of
`DerivedCoreProperties.txt`.

**Step 2 is the one the acceptance item is about: the COMPILER reads the
UCD.** `tools/ucd/gen_ucd.fi` holds 16 + 8 `comptime` blocks that call
`file_size`/`file_byte` on the two files, parse them **inside the compiler**
and write Firn source text out of them with `emit_raw`/`emit_number`:

```
-- 2. the compiler reads the UCD at compile time --
   emitted Firn source text: 222414 octets, 8746 lines
   time for the comptime run: 3244 ms
```

Why 16 + 8 blocks and not one: `compiler/src/comptime.rs` allows
`MAX_STEPS = 2,000,000` executed statements per block (SPEC 14.1.comptime,
„a comptime must not hang the compiler"), and a fresh interpreter is built
per block. Round 85 measured the budget rather than assuming it (400,065
octets go through in one block, 500,000 do not) and split
`UnicodeData.txt` into eight windows for the general category alone. This
round parses **more of every line** — fields 12 and 13, the two simple case
mappings — and therefore takes sixteen. `tools/ucd/expand_tables.py` computes
the window boundaries and **nothing else**; it does not know a single Unicode
category, and it never splits between a `<…, First>` line and its `<…, Last>`
partner.

`DerivedCoreProperties.txt` is the second file because `ID_Start` and
`ID_Continue` are **derived** properties: they cannot be computed out of
`UnicodeData.txt` without repeating the derivation, and repeating a
derivation is how you get a table that is almost right. The blocks match the
property name octet for octet — `XID_Start` begins with an `X` and is
therefore not matched, which is what the very first comparison is for.

What comes out is one line per entry:

```
   entries read out of the UCD: 8610
     categories 3423, ID_Start 776, ID_Continue 1418, upper 1505, lower 1488
```

**Step 4 packs it.** `tools/ucd/pack.fi` is a Firn program — there is no
Python in the path from the UCD to the table. It cannot be a `comptime` block
and the reason is written in `compiler/src/comptime.rs`: `comptime` has
integers and bools and nothing else. A table with deduplicated blocks needs a
1,114,112 octet array and a search over the blocks kept so far; neither
exists there. Reading the UCD is what the item asks of the compiler, and that
happens in step 2.

**Step 5 is firnfmt.** The generated file has to be in canonical shape,
otherwise `tools/fmt/run.sh` fails over a file nobody typed. The packer
writes canonical Firn straight away; the step checks it with `firnfmt -c`
instead of trusting it.

## 3. The shape of the table, measured against the alternatives

Three loads, no loop, the same cost for every code point:

```
level 1   cp >> 9          2,176 entries of one octet   -> a level 2 block
level 2   (cp >> 4) & 31   32 entries of two octets     -> a level 3 block
level 3   cp & 15          16 entries of one octet      -> the class octet
```

The class octet answers three questions at once: bits 0..4 the general
category (0 = Cn), bit 5 `ID_Start`, bit 6 `ID_Continue`. Blocks that are
equal octet for octet are stored once — the unassigned planes 4 to 13 cost
almost nothing.

The block sizes were **chosen by measurement, not by taste.** The same data,
packed in every shape that fits:

| shape | octets |
|---|---:|
| two stages, blocks of 32 | 89,056 |
| two stages, blocks of 64 | 62,336 |
| two stages, blocks of 128 | 50,816 |
| two stages, blocks of 256 | 45,824 |
| three stages, 64 / 8 | 31,344 |
| three stages, 32 / 32 | 24,800 |
| **three stages, 16 / 32** | **20,256** |
| three stages, 16 / 64 | 21,152 |

Plus the case mappings, which are sparse and get a different shape: runs of
`lo`, `hi`, a stride of 1 or 2 and a delta, one `u64` each (204 + 186 runs =
3,120 octets), with an index by `cp >> 10` (2 × 256 octets). The stride of 2
is not a trick — it is what the UCD is made of, where a whole Latin
Extended-A block pairs even and odd code points.

```
   the table at run time : 23888 octets
     level 1             : 2176 octets (one per 512 code points)
     level 2             : 103 blocks x 64 octets = 6592 octets
     level 3             : 718 blocks x 16 octets = 11488 octets
     case mappings       : 204 + 186 runs x 8 octets = 3120 octets, plus 2 x 256 octets index
   the generated source  : 100826 octets, 3020 lines
   words written         : 2898 of 2986 (the zero words come from mmap)
```

Stage 0 has no global arrays (SPEC 14.1 item 5), so the table is written into
a mapped area at run time — the same way the character reference table of the
HTML tokenizer is (`lib/html/entities_data.fi`), with `mmap` **without**
`MAP_FIXED`. Only the 2,898 words that are not zero are written; the rest
comes zeroed from the kernel.

## 4. The lookup time

`tools/ucd/bench_tables.fi` asks both tables the same 20 million code points
in the same order. The old table is kept as `tools/ucd/flat_baseline.fi` —
a comparison whose other side has been deleted is not a comparison.

| measurement | run 1 | run 2 | run 3 | run 4 |
|---|---:|---:|---:|---:|
| set up, flat (2,802 pushes into a heap buffer) | 162.7 us | 171.1 us | 183.4 us | 161.2 us |
| set up, table (`mmap` + 2,898 words) | 56.5 us | 52.2 us | 52.9 us | 49.9 us |
| the loop alone (random number + branch) | 11.7 ns | 11.9 ns | 20.3 ns | 12.7 ns |
| `latin`, flat (binary search) | 78.3 ns | 82.5 ns | 90.5 ns | 93.7 ns |
| `latin`, table (three loads) | 22.9 ns | 24.1 ns | 37.8 ns | 28.7 ns |
| `wide`, flat | 84.0 ns | 163.6 ns | 90.5 ns | 103.5 ns |
| `wide`, table | 19.7 ns | 40.9 ns | 21.4 ns | 32.5 ns |
| upper case mapping, table (the flat one cannot) | 14.8 ns | 30.7 ns | 15.8 ns | 27.8 ns |

**The machine was busy** while these ran — the endurance run of section 6 the
whole time, and two other rounds building in their own worktrees; the load
average was around 10 on 8 cores. That is why four runs stand here instead of
one number, and why the spread is wide (`wide`, flat: 84 to 164 ns). The
RATIO is what survives it: the flat list costs **3.4x to 4.3x** of the table
in every single run, and no run has it the other way round.

Taking the least loaded run and subtracting the loop: **66.6 ns against
11.2 ns** on `latin` and **72.3 ns against 8.0 ns** on `wide` — 5.9x and
9.0x. The table is also **3.1x to 3.5x faster to set up**, which matters
because it happens once per `Lexer` and once per `Realm`.

The two distributions differ on purpose:
`latin` (0x80…0x24F) is what a lexer really meets, and the binary search
stays in its hottest entries there; `wide` walks the whole code space and the
binary search touches cold cache lines.

**The other number in that table is the one that matters more.** Over 20
million random code points the old table answers `ID_Start` **2,369,251** times, the
new one **2,620,597** times. That is not noise — it is three Unicode versions of
characters that the JavaScript lexer did not know.

## 5. What the engine does with it

`lib/str/ucd.fi` maps the table and holds the three loads. The pointer is
handed around, not global: the `Lexer` carries it where the two range buffers
used to sit, and the `Realm` carries it next to `ctx`, `names` and `tree`.
A null pointer means „the mapping failed", and every lookup then answers as
if the code point were unassigned instead of reading from address zero.

test262, both engines built from the same compiler, run in person on the
directories that touch these tables:

| directory | before | after |
|---|---:|---:|
| `language/identifiers` | 463 / 535 | **535 / 535** |
| `String/prototype/toUpperCase` | 44 / 52 | 46 / 52 |
| `String/prototype/toLowerCase` | 48 / 60 | 50 / 60 |
| `String/prototype/toLocaleUpperCase` | 44 / 52 | 46 / 52 |
| `String/prototype/toLocaleLowerCase` | 44 / 56 | 48 / 56 |
| `String/prototype/trim` | 256 / 258 | 256 / 258 |
| `String/prototype/trimStart` | 44 / 46 | 44 / 46 |
| `String/prototype/trimEnd` | 44 / 46 | 44 / 46 |
| **total** | **987 / 1,105** | **1,069 / 1,105** |

The two cases per direction that came with the case mapping are the
supplementary planes: the conversion now works on code POINTS, so `U+10428`
uppercases to `U+10400` instead of coming back unchanged.

**The sample of `tools/js/run.sh --fast` contains none of these
directories** (it is `language/types`, `asi`, `block-scope`, `literals`,
`white-space`, `line-terminators`, `comments`, `punctuators`,
`reserved-words`, `keywords`, `rest-parameters`, `destructuring`,
`built-ins/Math`, `JSON`, `Boolean`, `NativeErrors`), so its numbers are
**unchanged at 3,049 parser and 2,603 engine**. That is said here rather than
left for somebody to notice.

**What is still missing, and is not pretended otherwise:**

* `SpecialCasing.txt` — the full mappings, where one code point becomes
  several (`"straße".toUpperCase()` is `"STRASSE"` in a complete engine and
  stays `"STRAßE"` here). `UnicodeData.txt` leaves field 12 empty for exactly
  those characters, so the simple mapping does not invent a wrong single
  character; it leaves them alone. `special_casing.js` therefore still fails.
* `CaseFolding.txt` — for `/u` and `/v` the standard asks for simple case
  FOLDING, not for the upper case mapping. The engine uses the upper case
  mapping for both, as it did before. The difference shows on characters
  whose folding and whose upper case differ (`U+00DF`, `U+1E9E`).
* `String.prototype.normalize` still has no decomposition tables.

## 7. What the rescan of the roots costs

On 2026-08-24, commit `47690a8a` closed a real hole in the collector: the
incremental cycle scanned stack and registers once, at `__gc_cycle_start`,
and the Dijkstra insertion barrier does not cover the other direction — an
object READ out of a heap field and then removed from it stayed white and was
swept while the mutator still held it. Since then the roots are looked at a
second time before the sweep. This round is the first long load after that,
and the price is a number here rather than an opinion.

Both sides ran **side by side** — same load, same seed, same machine, same
minute — from two compilers that differ in exactly the two call sites of
`__gc_roots_rescan` (`bash tools/gc_soak/run.sh --ab 1800` builds the second
one, removes the two lines with a check that there really were two, and puts
`lib/gc/gc.fi` back afterwards):

| | with rescan | without |
|---|---:|---:|
| duration | 30m 04s | 30m 00s |
| rounds | 14,021,632 | 15,438,848 |
| collections | 13,023 | 14,360 |
| longest mark slice | 67.81 ms | 70.08 ms |
| longest sweep slice | 12.12 ms | 14.40 ms |
| **longest whole interruption** | **114.26 ms** | **73.98 ms** |
| RSS median, last quarter | 27,288 KiB | 28,200 KiB |
| heap / live, median | 2.48x | 2.55x |

**Throughput without the rescan: 1.104x.** At 13,023 collections in half an
hour that is about 13 ms of mutator time per collection — a live set of
around 11 MiB is traced from the roots a second time, and under this load
that is what it costs. It shows up in the whole interruption (114 ms against
74 ms) and **not** in the longest mark slice, because the rescan runs after
the slice has been booked.

That is the price of a collector that does not release memory the mutator is
still holding. The alternative named in the commit message — a deletion
barrier (Yuasa) on every pointer READ — would cost on every read instead of
once per cycle. Nothing here says the current trade is the best one; it says
what it costs.

## 8. What this round did not do

* No `SpecialCasing.txt`, no `CaseFolding.txt`, no normalization tables
  (section 5).
* The `comptime` step budget was not raised. Sixteen windows over
  `UnicodeData.txt` are a workaround for a limit of 2,000,000 statements per
  block, and the honest fix would be a `comptime` that can carry an array.
* `lib/html/` is unchanged, on purpose (section 1).
* The general category is in the table and is used for `Zs`/`Zl`/`Zp` only.
  Nothing else asks for it yet.
