# DNS and https by name (round DNS)

Until this round `net.http` could fetch from `http://127.0.0.1:8080/` and
from nothing that has a NAME: `HttpError::Resolve` was the answer to every
host name, and `https://` was refused outright. The first consumer is
FleiLauncher (Minecraft launcher in Firn/fUi), which has to talk to
`piston-meta.mojang.com`, `api.modrinth.com`, `resources.download.minecraft.net`,
`login.microsoftonline.com` and friends.

## Modules

| module | file | what |
|---|---|---|
| `net.udp` | `lib/net/udp.fi` | UDP sockets (IPv4): `udp_open`, `udp_bind`, `udp_sendto`, `udp_recvfrom` (reports the sender), `udp_set_timeout`, `udp_close`. Results are `i64`: >= 0 or the negated errno. Same system calls on Linux and Windows (the seam translates them). |
| `net.dns` | `lib/net/dns.fi` | the resolver, see below |
| `net.dnsconf` | `lib/net/dnsconf.fi`, `dnsconf.windows.fi` | where the servers and the hosts table come from: `/etc/resolv.conf` and `/etc/hosts`; on Windows `GetNetworkParams` (made into resolv.conf text, so one parser serves both) and `C:\Windows\System32\drivers\etc\hosts` |
| `tls.trust` | `lib/tls/trust.fi`, `trust.windows.fi` | the system's root certificates: first PEM bundle that exists (Debian, Fedora, openSUSE, Alpine paths); on Windows the `ROOT` and `AuthRoot` stores through crypt32, plus `cacert.pem` in the current directory |
| `net.http` | `lib/net/http.fi` | `https://`, host names, every address of an answer tried in turn |

`lib/net/dns_main.fi` is the resolver as a program (`dns_main [-s ip[:port]] [-6] name...`).

## The resolver

```firn
var res: dns.Resolver = dns.resolver_new()
dns.resolver_init(&res)                 // servers + hosts table from the system
var out: dns.Resolved = dns.resolved_new()
let ok: bool = dns.dns_resolve_a(&res, host_ptr, host_len, &out) catch false
// out.addr[0 .. out.n], host order (the net.ipv4 form); out.via says where it came from
```

* Order of sources: numeric IPv4 -> `localhost`/`*.localhost` -> hosts table -> cache -> servers.
* Wire format of RFC 1035 incl. name compression (pointer hop limit 16, forward and
  out-of-range pointers refused, label types 01/10 refused). `dns_build_query`, `dns_parse_reply`
  are pure functions over octets.
* A and AAAA. CNAME chains are followed inside one answer (any record order) and across answers (a CNAME with no
  address behind it starts a new question), at most 8 links; a cycle is `CnameLoop`. Records that are not on the
  chain of the question are dropped.
* UDP with a per-attempt timeout that doubles (default 2 s, 2 attempts, cap 8 s), every server in turn.
  A reply counts only if it comes from the server asked, on port 53, with our ID and our question.
  TC set: the same question over TCP. SERVFAIL/REFUSED: next server; if every server says so, no retry round.
* Transaction ID: 16 random bits from the kernel (`std.crypto.random`); the source port is chosen by the kernel.
* Cache: 32 names, positive (TTL 1..3600 s) and negative (30 s), monotonic clock.
* Errors: `Name NoServers Timeout Network Format ServerFail NxDomain NoData CnameLoop Random`;
  `resolver_last_error` gives the number for the caller that cannot name the variant.
* No configured server -> 1.1.1.1 and 8.8.8.8 (never added to a configured list).

## https

`net.http` opens TLS 1.3 (`lib/tls/tls.fi`) for `https://`. The certificate chain and the HOST NAME are
checked against the roots of `tls.trust` plus anything added with `client_add_trust_pem`; no roots means
`HttpError::Tls`, never a downgrade and never an unchecked connection. There is no switch that turns the
check off. `client_tls_error` / `client_tls_verify` say why a handshake failed.

**secp256r1.** `tls.fi` used to offer X25519 only. `piston-meta.mojang.com` (Azure Front Door) has no X25519 and
answers handshake_failure (`openssl s_client -groups X25519` shows the same). Both key shares now go in the
first flight; ECDHE on P-256 uses `std.crypto.p256` (constant-time ladder) and the server's point is checked to lie
on the curve (`ecdsa.point_valid`).

## Honest limits

* IPv4 transport only (D1); no DNSSEC/DoT/DoH/EDNS0, no 0x20 (D2); no search list (D3); no IDN, convert to
  punycode first (D4); the cache is per resolver and not thread-safe (D7, D8).
* TLS 1.3 only: servers that still speak TLS 1.2 only are unreachable (`login.live.com`, `*.badssl.com`).
* Windows: enumerating the certificate store is not what Windows' own chain building does; roots Windows adds on
  demand may be missing. Ship `cacert.pem` next to the program for those machines. Measured here only under Wine
  (the machine FLEI-ONE is not reachable from the server for a file transfer).
* No TLS session resumption, no HTTP/2.

## Proof

* `tests/2090_dns_wire.fi` (generated by `tools/dns/gen_test.py`): real answers of 1.1.1.1 with the expected values
  from an independent Python decoder, hostile messages (loops, lying pointers, off-chain records, cycles, TC),
  query bytes, name rules, strict dotted quads, resolv.conf and hosts parsing.
* `tests/2091_dns_loopback.fi`: a DNS server (UDP and TCP threads) in the test process; cache, chains, TC to TCP,
  NXDOMAIN, SERVFAIL, retry, forged answers (wrong ID, right ID from another port), two servers, TTL expiry, AAAA,
  the IDs are not constant. Mutations of `dns.fi` were checked to fail it.
* `tools/dns/run.sh`: fake DNS in Python (server log counted), the real network, https by name against a hermetic
  Python TLS server with counter-checks, `piston-meta.mojang.com` / `api.modrinth.com` / GitHub against curl, then
  the Windows build under Wine.
