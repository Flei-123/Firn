# lib/input -- reading the keyboard and mouse (round gpu-c, 12.10.2026)

Injecting input (uinput / SendInput) was already there: `input.input`. This round adds READING.

## What is there
- `window.raw_input(w, true)` (lib/window): `EV_RAWKEY` / `EV_RAWKEY_UP` for EVERY key (ev_a = Linux scancode, ev_x = keysym without modifiers, ev_y = time ms, ev_state = modifiers), `EV_FOCUS`, plus release/enter/leave. The old `EV_KEY` / `EV_CHAR` follow unchanged.
- `input.raw` (lib/input/raw.fi): per frame down / pressed / released for keys and mouse buttons, wheel, position, relative delta, auto-repeat filter (X11 release+press with equal time, Windows press without release), focus loss releases everything. Pure core `raw_feed` (tests/2793: scripted + 2000 random frames vs a model).
- `input.grab` (lib/input/grab.fi) over `window.cursor_mode(CURSOR_CAPTURED)`: invisible cursor, pointer kept in the window.
  - X11: pointer grab + XInput2 RawMotion (unaccelerated); fallback warp-to-centre with the warp-echo fix. No EV_MOTION while captured.
  - Windows: ClipCursor + RegisterRawInputDevices/WM_INPUT; fallback pointer position against the middle.
  - `window.cursor_shape(w, SHAPE_*)` (X11 cursor font glyphs, Windows IDC_*); `cursor_raw` / `cursor_is_raw`.
- Server quirk found: with a pointer grab Xorg/Xvfb delivers every raw event twice; identical neighbours are dropped (a real pair of identical events in the same ms with the same request sequence is lost; only 8 kHz mice could do that).

## Proven (tools/input/read_run.sh)
Xvfb + xdotool (XTest): 5x(10,-4)+3x(-7,20) sums to exactly (29,40) in raw AND warp mode; raw key a = scancode 30, keysym 97; the grab program builds for Windows.
NOT proven: invisible cursor (visual), real mouse/keyboard, Windows at runtime (Wine run of the probe stopped at window creation, not investigated), WM_INPUT, focus events under a real WM.

## Gamepads (round gpu-e, r420) -- lib/input/pad*.fi
- Layers: `input.padcore` (pure: evdev `input_event` 24 B / joydev `js_event` 8 B / XInput -> the logical SDL gamepad: 16 buttons `PB_*`, 6 axes `PA_*`, pressed/released edges, event ring `PE_*`), `input.padset` (8 slots + SDL GameControllerDB text), `input.padsys` (Linux: evdev first, joydev for devices evdev did not give, hot-plug by inotify on /dev/input + settle rescan; `padsys.windows.fi`: XInput via std.dynlib), `input.pad` (front door: `pad_open/pad_poll/pad_frame/pad_close`). Syscalls only on Linux (static ELF stays static).
- Mapping: `pad_apply_sdl` takes one SDL GameControllerDB line (Linux lines; `b`/`a`/`h`, `+a`/`-a` half axes, `a~` inverted, SDL evdev index order); a device without a line gets the kernel's gamepad codes (BTN_SOUTH.., ABS_RX.., hat0). `pad.pad_db_load(set, path)` adds a gamecontrollerdb.txt (lookup: full GUID, then bus+vendor+product). No database is shipped.
- Normalisation from EVIOCGABS ranges, radial deadzone for sticks (0.15), threshold for triggers (0.05), `pad_set_deadzone`. Events: connect/disconnect are never dropped (ring of 64, oldest goes). SYN_DROPPED: events up to the next SYN_REPORT are discarded and the key/axis state is re-read (EVIOCGKEY/EVIOCGABS).
- Proven (tests 2794/2795, tools/input/pad_run.sh, gate 127): byte parsing, SDL parsing, deadzones, joydev maps, XInput scaling, 4000 random events vs a model, the real non-blocking read path on a PIPE with fake bytes (random chunks, 170+ events per read, unplug = EOF), DB lookup. The Windows build of the front door compiles.
- NOT proven: any real pad (no /dev/input here), real hot-plug, permissions, XInput at runtime (not even Wine), joydev ioctls (JSIOC*), rumble / force feedback (not done), DirectInput/HID-only pads on Windows, aarch64 syscall numbers (x86_64 numbers like uinput.fi; getdents64/inotify forms not checked on aarch64).

## evdev raw keyboard / mouse (r421) -- lib/input/rawdev.fi
`rawdev_open` scans /dev/input/event* (keyboards: KEY_A+SPACE+ENTER, mice: REL_X/Y+BTN_LEFT; pads are left to input.pad), `rawdev_pump(&rd, &raw)` feeds `raw.raw_feed_ev` = the SAME state machine as the window events (repeat value 2 dropped; position only counts up from 0). Read only, no EVIOCGRAB, no focus needed (so it needs group `input`; `rawdev_denied` counts refusals). Windows twin = honest stub (use window.raw_input). Proven with fake bytes on a pipe (tests/2797, 2000 random frames); real devices NOT.

## Text input / IME (round gpu-k, r433) -- lib/input/textcore.fi, textsys(.windows).fi, composedata.fi
- `input.textcore` (pure, tests/2810): `Text` = pre-edit text (code points + XIM feedback word per code point + caret), segments (runs of equal class `SEG_INPUT/CONVERTED/TARGET`), an event ring (`TE_PREEDIT_BEGIN / PREEDIT / PREEDIT_END / COMMIT`, commits split at 32 code points, the oldest event goes when full), the text cursor rectangle (`text_set_spot` / `text_spot_take`), UTF-8 and UTF-16 helpers (ill-formed input -> U+FFFD). Platform input: `text_preedit_replace` (XIM's replace semantics), `text_preedit_set`, `text_preedit_caret`, `text_commit(_utf8)`, `text_preedit_commit` (finish composing), `text_preedit_cancel`.
- Compose engine `text_key(ks, mods)` for keyboards without an IME: dead keys (keysym 0xFE50.. + base letter = NFC letter; twice / space = accent; unknown = accent + letter) and the Compose key + 2-3 ASCII keys. Tables `composedata.fi` are GENERATED (`python3 tools/input/gen_compose.py > lib/input/composedata.fi`; 541 dead-key + 1147 sequence entries). Pre-edit text shows the waiting accent / typed keys.
- X11 `input.textsys` (Linux): libX11 by dlopen, SECOND connection with its own 1x1 unmapped window; real-window keys are replayed as synthetic XKeyEvents through `XFilterEvent` (`sys_key(down, X keycode = scancode + 8, X state, time)`), text from `Xutf8LookupString` -> commit; IME-originated commits arrive on the second connection (`sys_pump`). Style: pre-edit callbacks first (4 callbacks write into the Text), else the IME's own pre-edit window, else none. Locale: `setlocale(LC_ALL, "")` + `XSetLocaleModifiers("")` (XMODIFIERS). `sys_spot` forwards the cursor rectangle as XNSpotLocation (stops after the first refusal). Keys the IME did not turn into text but that are dead keys / Compose go to the engine above.
- Windows `textsys.windows.fi`: IMM32 via dynlib: `sys_ime_message(WM_IME_COMPOSITION / ENDCOMPOSITION)` reads GCS_COMPSTR / ATTR / CURSORPOS / RESULTSTR into the Text, `sys_spot` -> ImmSetCompositionWindow + ImmSetCandidateWindow. Builds only; `lib/window/win32.fi` does not forward WM_IME_* yet (WM_CHAR still delivers finished characters).
- Android (r70, NOT changed here): lib/android/inputmethod.fi already serves the InputConnection. Mapping to the Text API: `setComposingText(s, n)` -> `text_preedit_set_utf8(s, caret)`; `commitText` -> `text_commit_utf8`; `finishComposingText` -> `text_preedit_commit`; `deleteSurroundingText` needs the surrounding text of the field (not part of the Text; stays with fUi's textbuf); the cursor rectangle -> `updateCursorAnchorInfo` (`text_spot_take`). fUi (lib/fui/ime.fi) hooks: filter = `sys_key` result, spot = `text_set_spot`, results = `text_preedit_utf8` + `text_preedit_caret_bytes` -> `editor_ime_preedit`, TE_COMMIT -> `editor_ime_commit`.
- Proven (gate 130, tools/input/text_run.sh): tests/2810 (every table entry found by the binary search, directed dead-key / Compose cases, segments, UTF-8 view, ring overflow, 30000 random operations against a linear-scan model; a mutant is caught), tests/2811 (the four XIM callbacks called through their C addresses with hand-made XIMPreeditDrawCallbackStruct / XIMText, multibyte + wide text, deletion, hostile negative numbers, style choice), xim_probe on a private Xvfb with `@im=none`: style PreeditNothing|StatusNothing, plain and Shift keys become commits through the real Xlib. Windows build compiles (not run).
- NOT proven: ANY real IME (ibus, fcitx, uim, Windows IMM/TSF, Android); the pre-edit callbacks driven by a real server (only by hand-made data); dead keys / Compose through Xlib's built-in IME (this Xvfb refuses keymap changes: xmodmap / setxkbmap / xkbcomp had no effect, so no key is a dead key); XNSpotLocation acceptance; a mapped input window (it is unmapped; some XIM servers may want it mapped); wiring into lib/window (the host feeds EV_RAWKEY into `sys_key` itself).

## Wiring + surrounding text (round gpu-o, r444 part 1)
- `plat.fuitext` (lib/plat/fuitext.fi): glue between a window and a fUi field. `ft_open(f)` switches `window.raw_input` on (and on Windows `window.ime_events`), opens textsys; `ft_event` takes EV_RAWKEY / EV_RAWKEY_UP / EV_FOCUS / EV_IME from the input hook (`fuiwin` now forwards these four kinds to the hook, answer ignored, a modal menu gets no raw presses), `ft_swallow` drops the EV_KEY / EV_CHAR of a key the input method ate or whose text a field took (no double text; Ctrl / Alt / Super are never replayed), `ft_pump` serves IME-sent events, `ft_spot` / `ft_surround` pass the caret rectangle and the surrounding text. The sink (`ft_set_sink`): pre-edit (UTF-8 + caret octet) -> `editor_ime_preedit`, commit -> `editor_ime_commit`, cancel -> `editor_ime_cancel` (a cancel directly followed by a commit is dropped: the commit replaces the pre-edit text), delete -> `editor_delete_surrounding`.
- Windows: `window.ime_events(f, true)` makes win32.fi swallow WM_IME_STARTCOMPOSITION / COMPOSITION / ENDCOMPOSITION and queue them as `EV_IME` (a = message, x = GCS_* flags); `window.ime_handle(f)` = the HWND. fuitext then calls `textsys.sys_ime_message` (the IMM context is read AFTER the message, from the main loop). Other back ends answer false / 0.
- Surrounding text (textcore): `text_set_surrounding(p, n, cursor, anchor)` keeps a window of <= SURMAX = 1024 octets on code point borders (`text_surround_*` getters, cursor as code points / UTF-16 units); `text_delete_surrounding(before, after, SU_BYTES | SU_UTF16 | SU_CP)` clamps, never cuts a character (a UTF-16 pair that does not fit stays), queues `TE_DELETE_SURROUNDING` (cp[0] octets before, cp[1] octets after) and updates the window. Field side: `editor.editor_delete_surrounding(before, after)` (octets around the SELECTION, RES_NONE while a pre-edit text stands), `editor.editor_ime_cancel`.
- Android mapping unchanged (see above): `deleteSurroundingText(b, a)` -> `text_delete_surrounding(b, a, SU_UTF16)`; the surrounding text is given with `ft_surround` / `text_set_surrounding`.
- Proven: tests/2813 (surrounding window, units, boundaries, long text, editor deletion, cancel), fuitext builds for Linux / Windows; window back end changes build for Linux, Windows, x86_64 / aarch64 Android; tools/input/text_run.sh stays green (gate 130).
- NOT done: the call sites in `lib/@linux/fui/apphost.fi` (on_input must call `ft_event` / `ft_swallow`, run must `ft_open`, `ft_set_sink` with app.fi functions that act on `focused_slot`, `ft_pump` + the XIM connection fd in the wait, caret rectangle from `draw_entry` via `render.field_caret_x` / `field_line`), so a fUi program still types through EV_CHAR; the Xvfb + xdotool fUi test; any real IME / Windows run.

## apphost wiring (round gpu-t, r444b) -- lib/@linux/fui/apphost.fi, lib/plat/fuiime.fi
- OPT IN: `import plat.fuiime` + `fuiime.enable()` before `app.run`. apphost itself does NOT import `plat.fuitext` (it pulls in `std.dynlib` = libX11: the image would become a dynamically linked ELF and `aarch64` builds would fail), so fUi programs stay static unless they opt in; apphost keeps an `ImeBind` function table (`apphost.ime_install`). `FUI_NO_IME=1` switches it off at run time. Android and web apphosts never call it.
- What apphost does with it: `ft_open` after `window_open`, the sink = app.fi functions on `focused_slot` (`app_ime_pre/commit/end/del`, via `hooks_set_ime`); `on_input` sends EV_RAWKEY / _UP / EV_FOCUS / EV_IME to `ft_event` and drops EV_KEY / EV_CHAR through `ft_swallow` (no double text); `ft_pump` once per loop turn; the XIM connection (`textsys.sys_fd` = XConnectionNumber, `fuitext.ft_fd`) is polled next to the window's descriptor (`window.wait_any_fd`, `fuipopup.ph_wait_fd`); the caret rectangle painted by `draw_entry` (`note_spot`: `render.field_caret_x` / `field_line`, text areas `ta_caret_box`) goes to `ft_spot` when it moves.
- Mouse click (or another field getting the focus, Tab) while pre-edit text stands: the field keeps the text as it is (`editor_ime_end` via `hooks.ime_confirm`), then `fuitext.ft_reset` = `XmbResetIC` + drops the Text's pre-edit state.
- Proven (gate 136, tools/input/apphost_run.sh, the REAL window on a private Xvfb, xdotool, `@im=none`, program tools/input/fui_ime_main.fi): typing, dead key acute+e -> e-acute, Compose o c, pre-edit + replace + commit in the field, click during pre-edit (text kept, a lost dead key does not leak: plain `e` follows), Tab during pre-edit, `FUI_NO_IME=1`, plain fUi programs still static. The pre-edit texts come from the test program feeding textcore (F5) -- `@im=none` sends no pre-edit callbacks. Windows build of the test program compiles.
- NOT proven: a real IME (ibus / fcitx / Windows IMM), the candidate window position (XNSpotLocation acceptance), `ft_surround` is not called by apphost yet (surrounding text for IMs that ask), XIM reset of IMM32 (Windows `sys_reset` is a no-op), a window manager.

## Rumble (round gpu-t, r434) -- lib/input/padff.fi, padsys(.windows).fi, pad.fi
- API (`input.pad`): `pad_rumble_supported(set, i)`, `pad_rumble(set, i, strong 0..1, weak 0..1, ms)`, `pad_rumble_stop`, `pad_rumble_gain(set, i, 0..1)`. ms 0 = the longest (65535 ms). Both magnitudes 0 = stop. Closing the set stops the rumble and erases the effect.
- Linux evdev force feedback: the node is opened read+write (`ev_open_rw`, falls back to read only = no rumble), `EVIOCGBIT(EV_FF)` must show `FF_RUMBLE`; `EVIOCSFF` uploads a 48-octet `ff_effect` (id -1 = new, the kernel returns the id; later calls re-upload the SAME id = change in place), play / stop = write of an `input_event { EV_FF, id, 1 / 0 }`, gain = `{ EV_FF, FF_GAIN, 0..65535 }`, cleanup = stop + `EVIOCRMFF`. joydev has no force feedback: honest false.
- Windows: `XInputSetState` (loaded next to XInputGetState); no duration in XInput, so the end is a deadline checked in `sys_poll`; the gain scales the magnitudes.
- Proven: tests/2866 (byte layout of ff_effect / input_event, ioctl numbers, ff_scale / clamp; padsys call ORDER through `sys_ff_tap`: upload, play, in-place change, gain, stop, close = stop then erase, no-FF / joydev / empty slot = false and nothing sent), gcc cross-check in pad_run.sh (sizeof / offsetof of `struct ff_effect`, EVIOCSFF / EVIOCRMFF / EVIOCGBIT equal padff.fi), Windows build of the front door with rumble. Gate 127.
- NOT proven: any real pad (the real ioctl / write calls never ran against a kernel), permissions (group `input` / uaccess for read+write), whether length 0xFFFF plays to the end on every driver, XInputSetState at runtime (not even Wine), aarch64 ioctl numbers (same as x86_64 for these generic ones, not run).
