# fUi GPU path with CPU fallback (concept, W18-E)

## Rule
- The CPU rasteriser stays the DEFAULT and the reference. The GPU path is opt-in (`FUI_GPU=1`) and may only be switched on when its output is pixel-near to the CPU frame.
- Every GPU failure (no GL library, shader compile error, context lost) falls back to the CPU painter for the rest of the run; the window keeps its content (a full repaint follows).

## What exists
- `lib/fui/gpu.fi` (Gpu, targets, `gpu_attach(g, canvas)`, `gpu_flush`), shaders `gpu_vs.glsl`, `gpu_fs*.glsl`, `lib/plat/gles.fi`. Works on Android (GLES) and the web build; X11/Windows/OrientOS answer "no" because no system GL is loaded (r156).
- `painter_clear`, `surface`, `round_rect` already branch on `gpu.gpu_of(canvas)`: a canvas with a Gpu is painted by the GPU, else by the CPU.

## Minimal entry (next steps, smallest first)
1. `gpu.gpu_probe(api) -> bool`: try to open the system GL (needs a way to load libGL/libEGL: Firn programs are linked statically and have none yet, see the header of `gpu.fi`; first step may be a tiny helper process or a Firn dynamic loader), create a 16x16 target, clear, read back one pixel. Pure yes/no, no window. Test: on a host without GL it returns false and the program continues on the CPU.
2. Host switch in `apphost`: `FUI_GPU` unset or 0 -> never touch GL. 1 -> probe; true -> `gpu_attach`, false -> CPU (print one line to stderr).
3. Parity gate `tools/fui/gpuparity.sh`: paint the showcase sheets once on the CPU and once through the GPU path (llvmpipe / Xvfb+GLX is enough), compare per channel; threshold: mean abs diff <= 1.0, max diff <= 12 (AA / blur rounding), glyph pixels excluded until the GPU text path matches the CPU glyph cache. CPU frames stay golden-exact (`showcase.sh`).
4. Fallback test: force a failing shader (env `FUI_GPU_FAIL=compile`) -> frame must equal the CPU frame bit for bit.

## Not in scope here
- Glass blur / merge groups on the GPU (r71, r244 offline), Vulkan (`tools/gpu/vk`).

## Vulkan backend (W18-F): measured facts + the plan that fits the code
- DONE: `tools/fui/gpu_probe_main.fi` -- loader, instance, device (Mesa lavapipe 1.3 here), 16x16 clear + read-back: OK. Run with `XDG_RUNTIME_DIR` set. Exit 4 = no Vulkan (gate prints SKIP).
- DONE: `lib/fui/spv/build.sh` turns the SAME GLSL ES sources of the GLES backend (`gpu_vs.glsl`, `gpu_fs.glsl`, `gpu_fs_photo.glsl`) into Vulkan SPIR-V (committed `gpu_vk.vert.spv`, `gpu_vk.frag.spv`, `gpu_vk_photo.frag.spv`, spirv-val clean). Interface: set 0 binding 0 std140 block `P { vec2 u_size; vec2 u_srcsize; int u_nspot; vec4 u_spot[8]; }` (160 octets), bindings 1/2/3 = `u_atlas`/`u_stream`/`u_src` (combined image sampler), varyings `v_c0 v_c1 v_g v_p v_t v_clip v_k` = locations 0..6, vertex inputs 0 (vec2 corner, per vertex) + 1..8 (vec4, per instance, stride 128).
- DONE (W18-F2, lavapipe): `lib/fui/gpu_vk.fi` = a `paint.gl.GlApi` table filled by Vulkan (the table is only ~42 slots), so `gpu.fi` (batching, atlas, glass/frost passes, read-back) runs unchanged on X11/Windows/OrientOS. Design decisions:
  - Memory layout of GL and Vulkan agree WITHOUT any viewport flip (texel row 0 = NDC y -1, `gl_FragCoord.y` counts the same way), so the shaders and `gpu_read` stay as they are.
  - All images stay in layout GENERAL (render pass initial = final = GENERAL, descriptors use GENERAL): no layout tracking.
  - Every GL operation that touches the GPU (draw, clear, upload, blit, read) is ONE command buffer, submitted and fenced (`vk_frame.imm_begin/imm_submit`); descriptor set and uniform buffer are rewritten per draw. Simple and correct; batching is gpu.fi's job already (one instanced draw per batch).
  - Clear (also with scissor, `gpu_clear_rows`) = render pass with loadOp CLEAR and renderArea = scissor. Blit/copy = `vkCmdBlitImage` (X_CMD_BLIT). Blend = premultiplied (ONE, ONE_MINUS_SRC_ALPHA) -> needs one new blend mode in `vk_desc.pipeline_make`; `PipeSpec` has only 6 attribute slots, this pipeline needs 9 (enlarge to 12).
  - Program 1 = main FS, program 2 = photo FS (tell them apart by the length of the fragment source); uniform locations are (program << 8 | slot); `uniform1i` on a sampler = texture unit; a program owns its 160-octet uniform image. Texture units 0..2 -> bindings 1..3 (photo: `u_src` = unit 0 -> binding 3); unbound units get a 1x1 dummy.
  - Present: FB 0 is not a window; X11/Windows hosts call `gpu_read` and use their normal CPU present (or a swapchain blit later).
  - Fallback: `FUI_GPU_FAIL=open|compile` makes the table's open / `program` fail -> `gpu_open` false -> the CPU painter keeps running, frame bit-equal to a CPU-only run.
- GATE `tools/fui/gpuparity.sh` (zoo page of gpuzoo_web.fi, CPU vs Vulkan, light + dark, with and without text): mean 0.005, max 11 without text; with text 0.04 per mille of the pixels over 32 (largest 46, glyphs); `FUI_GPU_FAIL=compile|open` -> second CPU run bit-equal. lavapipe is a CPU: this proves the arithmetic, not the speed.
- DONE (W18-F3): HOST SWITCH `FUI_GPU=1`. `fuiwin.window_set_gpu_provider(fx, open, alive, close)` (function pointers, no dynlib import in fuiwin.fi) + `lib/plat/fuiwinvk.fi` (`window_use_env(&fx)` before `window_open`; a program that imports it becomes a dynamically linked ELF, every other fUi program stays static). In `gpu_start`, when the window layer has no GPU of its own, the provider fills the GL table (Vulkan), `gpu_open` + `gpu_attach`, `gpu_rb` = read-back mode: full repaint per frame, `gpu_read` of the whole canvas, then the normal CPU present. AUTOMATIC CPU FALLBACK: no Vulkan / `FUI_GPU_FAIL=open|compile` / no canvas target -> CPU painter from the start; a device that fails later (`vkgl_alive()` false after a failed submit; `FUI_GPU_FAIL=lost` fakes it at the 3rd read-back) -> that frame is painted again on the CPU, GPU dropped for the run. Gate `bash tools/fui/gpuhost.sh` (Xvfb): vk near CPU (PSNR 49.6, also after a resize), lost/open/compile bit-equal to the CPU run. `sh tools/fui/gpuparity.sh` and `gpuhost.sh` are in `tools/fui/run.sh` (SKIP without Vulkan / Xvfb).
- MEASURED (`gpuparity_main perf`, release build, lavapipe = software = CPU, load ~40, min of 3 rounds): page 1920x1080 (zoo + big elements) CPU painter 59.0 ms, Vulkan paint 154.4 ms + read-back of the canvas 16.1 ms; blur panel 400x300 r=18 CPU 1.46 / Vulkan 10.3 ms; 1200x700 CPU 9.3 / Vulkan 27.6 ms. These are NOT GPU timings; they show the overhead structure: ~570 submits + ~550 uploads per zoo page, every one waits for its fence, and the software-fallback bands (`gpu_upload_band`) upload ONE ROW per call (a submit each).
- DONE (W18-F3b): ONE COMMAND BUFFER PER FRAME in `gpu_vk.fi`. `cmd_open` starts recording on first use and appends (global barrier first), `cmd_close` only counts, `cmd_flush` submits + waits ONCE: at `read_pixels`, `finish`, `vkgl_close`, before anything a recorded command still uses is destroyed (`tex_release`, `fb_release`, `f_buffer_data`, `f_delete_obj`, staging regrow) and when a per-draw resource runs out. Per-draw state: pool of `SET_MAX` = 1024 descriptor sets + uniform slots (`UBO_STRIDE` 256: set k reads UBO octets [k*256, +160)); staging = bump allocator (`stg_alloc`, `bufferOffset` in the copy region, 16-octet aligned); a `GL_DYNAMIC_DRAW` vertex buffer is a ring of 8x its size (every `buffer_sub_data` writes a fresh window, the draw binds at it; gpu.fi always updates from octet 0 and draws what it wrote, so octets past the last update are not kept; `cmd_flush` leaves the newest window alone). Calls that may flush (`stg_alloc`, the set check) come BEFORE `cmd_open`. `gpu_upload_band` (gpu.fi) now copies the band flipped ONCE and uploads it with ONE `tex_sub_image_2d` (row-per-call only if no memory). Gate: output unchanged (gpuparity mean 0.005 / max 11, gpuhost ok) + stress in `gpuvk_main` (4096 draws = 4 pool refills, 40 x 1000 instances = ring wrap, 120 x 64 KB pictures = staging refills + upload texture replaced mid-recording; two deliberate bugs -- ring that does not advance, staging that does not advance -- are caught).
- MEASURED after (same machine, load ~20-25, lavapipe = CPU, min of 3 A/B rounds old/new): page 1920x1080 Vulkan paint 84.2 -> 61.4 ms (CPU painter ~30-35 ms); submits in the perf series 7244 -> 121, uploads 6582 -> 114; blur 400x300 7.2 -> 6.9 ms, 1200x700 18.5 -> 18.8 ms (shader work, unchanged). Still NOT a GPU timing: lavapipe runs the shaders on the CPU.
- NOT DONE (next): a real GPU (not lavapipe) is untested; consecutive draws into one target could share a render pass; Vulkan validation layer not installed here (no validation run).

## W39-a: swapchain present + Windows default policy (r360)
- DONE: `gpu_vk.vkgl_present_open/_present/_close/_vsync` (+ `vk.sc_set_vsync`, `vk_frame.imm_submit_sem`): the canvas target is blitted GPU-side into the swapchain image (negative source extent = row flip, image row 0 is the picture BOTTOM), acquire/present semaphores, then `vkQueuePresentKHR`. No read-back, no RGBA->BGRX, no PutImage. `fuiwin.window_set_gpu_present` (provider side), native handle from `window.native_handle` (HWND / XID; android/osum return 0 = read-back). Swapchain fails or stops showing -> closed, that frame takes the read-back path; device lost -> CPU (as before). `FUI_GPU_PRESENT=0` keeps read-back (A/B).
- POLICY (`fuiwinvk.policy`): `FUI_GPU=0` pure CPU, `1` Vulkan first (any device), `gl` window OpenGL first, `vk` Vulkan (real GPU only) first, unset = Windows `auto_policy` = OpenGL first, then Vulkan present on a real GPU, then CPU; other platforms stay CPU by default.
- MEASURED (Iris Xe, HOLO-LAPTOP-3, gpuhost hello, 200 frames, vsync off, median of 4, laptop busy with another worker + VirtualBox): 1920x1080 CPU 11.9 ms / GL 1.02 (submit) 1.40 (with glFinish per frame) / Vulkan present 1.84 (1.73 synced) / Vulkan read-back 16.5 (15.8); 1280x800 CPU 6.3 / GL 1.02 (1.34) / Vulkan present 1.63 (1.63) / read-back 9.2 (8.7). GL stays fastest, Vulkan present is the fallback; read-back is the last resort only.
- Gate: `tools/fui/gpuhost.sh` has vkp (swapchain picture == read-back picture, PSNR 99 = identical, also after resize) and lostp (device lost at present 3 -> CPU, canvas bit-equal). Software Vulkan (lavapipe/Xvfb) exercises the same code.
